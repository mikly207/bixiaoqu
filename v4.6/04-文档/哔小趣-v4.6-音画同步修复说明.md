# 哔小趣 v4.6 · 起播音画不同步修复说明

> 版本：v4.6（versionCode 46，versionName 4.6）
> 日期：2026-11-24
> 基线：v4.5（播放卡加载修复）

---

## 一、你反馈的现象

> "现在声音出来了，视频总是会慢一秒钟出来。"

即：点开视频后**先听到声音**，约 1 秒后画面才出现。这不是加载失败，是**起播时序错位**。

---

## 二、根因

DASH 高清播放是**音视频分离**的：画面走 VideoView，声音走独立的 MediaPlayer，两条流**并行准备**（这是 v4.1 为了提速做的优化，本身没错）。

问题出在"什么时候允许出声"：

```java
// 旧版（v4.1 ~ v4.5）音频 onPrepared
try {
    int vp = video.getCurrentPosition();
    ...
    mp.start();      // ← 音频一准备好就立刻出声
} catch (Throwable ignore) { }
```

**视频分片比音频慢**。原因很具体：

| | 音频轨 | 视频轨 |
|---|---|---|
| 数据量 | 小（~128kbps） | 大（1080P 约 2~4Mbps） |
| 首播需要 | 音频头 + 少量帧 | fMP4 的 moov + 首个关键帧 + 解码器初始化 |
| 典型就绪时间 | 100~300ms | 600~1500ms |

于是音频 200ms 就 `start()` 出声，画面 1 秒后才 `onPrepared` —— **声音抢跑了整整 1 秒**。

更糟的是，原有的音画校正 `syncAudio()` 有 **2.5 秒节流**（`if (now - lastAudioSync < 2500) return`），所以这 1 秒错位在开头会**持续存在**，直到 2.5 秒后才被拉回。

---

## 三、修复方案

核心原则：**并行准备保持不变（不牺牲启动速度），但音频必须"待命"而不是"抢跑"。**

### 1. 音频 onPrepared 不再直接出声

```java
// v4.6
audioPlayer.setOnPreparedListener(mp -> {
    audioPrepared = true;          // 只标记"我已备好"
    startAudioIfVideoReady();      // 画面没好就不出声
});
```

### 2. 等画面「首帧真正出图」才放音频

`onPrepared` 只代表流已就绪，**首帧还要等解码器出图**。所以画面 `onPrepared` 后不立刻放音频，而是轮询画面进度：

```java
void awaitFirstFrameThenStartAudio(int attempt) {
    ...
    int pos = video.getCurrentPosition();
    if (pos > 0 || attempt >= 12) {     // 进度推进 = 首帧已出图；300ms 兜底
        startAudioIfVideoReady();
        return;
    }
    ui.postDelayed(() -> awaitFirstFrameThenStartAudio(attempt + 1), 25);
}
```

> 为什么用轮询而不是 `MEDIA_INFO_VIDEO_RENDERING_START`：VideoView 在 `openVideo()` 里自己注册了 `OnInfoListener` 维护缓冲状态机，外部再 `setOnInfoListener` 会**覆盖**它，可能导致缓冲状态错乱。轮询 `getCurrentPosition()` 无侵入、更安全。

### 3. 统一出口 `startAudioIfVideoReady()`

所有"要不要出声"的判断收敛到一个方法：

```java
if (!audioPrepared || audioPlayer == null) return;   // 音频没备好
if (dashMode && player == null) return;              // 画面没 prepared，继续静音等
// 已就绪：按画面当前进度对齐后起播
```

### 4. 顺带修掉三处相关时序隐患

| 问题 | 修复 |
|---|---|
| 续播时音频 `seekTo` 与画面 `seekTo` 异步竞争，可能读到旧的 0 | 新增 `pendingAudioStartPos`，续播时直接用断点值，不依赖 `getCurrentPosition()` |
| 起播瞬间点暂停/播放，`togglePlay()` 会单独 `start()` 音频，又抢跑 | 新增 `audioStarted` 标记，**未起播的音频不允许被 toggle 单独拉起**，统一由起播回调放行 |
| `syncAudio()` / `doSeek()` / `setRate()` 在音频未起播时操作播放器，可能抛 `IllegalStateException` | 统一加 `audioStarted` 守卫 |

---

## 四、修复后的时序（三种情况都正确）

| 场景 | 行为 |
|---|---|
| **音频先备好（常见）** | 静音待命 → 画面首帧出图 → 音频从 0 起播 → **音画同帧** |
| **画面先备好** | 画面先播 → 音频后到时 `seekTo` 对齐到画面当前进度再出声 → 不从头播 |
| **画面永远不 prepared**（编码不支持） | 音频**一直不出声**（不再"有声音没画面"）→ 5 秒看门狗自动切兼容合流 → 正常有声 |

## 六、怎么确认真的修好了

装 v4.6 后打开视频，**声音和画面应当同时出现**，不再有"先听到声音、画面晚一步"的观感。

如果想看精确对齐数据，日志里有：

```
Android/data/com.bixiaoqu.app/files/boot.txt
```

会记录每次起播：

```
[play] ... audio start @v=42ms
```

`@v=` 就是音频起播时画面的进度（毫秒）。**这个值越小，说明对齐越准**（正常在 0~120ms 之间；如果看到 800ms+ 说明对齐失败，请把日志发我）。

## 七、调试开关（万一还有问题）

如果某台设备上仍然觉得音画有偏差，可以告诉我现象，我可以：

1. 把首帧等待的兜底从 300ms 调到 500ms（画面更慢的机型）
2. 把 `syncAudio()` 的 2.5 秒节流降到 1 秒（播放中更快纠正漂移）
3. 增加"起播阶段强制 seek 对齐"（更激进，但可能有轻微咔哒声）

当前版本先采用最稳妥的组合，避免引入新的副作用。
