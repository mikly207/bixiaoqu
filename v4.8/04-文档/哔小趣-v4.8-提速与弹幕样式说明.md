## 一、切换视频提速

### 1. 推荐列表自带 cid，却被白白丢掉（最大的一笔）

B 站的 `archive/related`（相关推荐）和 `popular`（热门）接口，返回的**每一项本身就带 `cid`**。但旧版 `loadRec()` 只取了 bvid/标题/封面，把 cid 扔了；切视频时 `play()` 发现没有 cid，只能再发一次 `pagelist` 请求去查。

```java
// 旧版
got.add(new VideoItem(bv, title, sub, pic));          // cid 丢了

// v4.8
long rc = o.optLong("cid", 0);                        // 直接用接口给的
got.add(new VideoItem(bv, title, sub, pic, rc, ra, dur));
```

**收益：每次点推荐少一次网络往返**（实测同类接口通常 150~600ms，弱信号下更久）。这条是"切换慢"最直接的原因之一，尤其连续切的时候，每次都白跑一趟。

### 2. 元数据与互动状态：4 次串行 → 三路并行

点进视频后，"标题/UP主/点赞数/投币数/关注态"原来是这样拿的：

```java
meta   = archiveMeta(bv);     // 等
like   = likeState(bv);       // 再等
coin   = coinState(bv);       // 再等
follow = followState(mid);    // 再等
```

4 次网络全串行，最坏要等 4 个往返互动数字才出来。v4.8 改成：

| 线程 | 任务 |
|---|---|
| meta-like | 查点赞态 |
| meta-coin | 查投币态 |
| 主线程（工作线程内） | archiveMeta → 拿到 mid → followState |

总耗时从 `meta+like+coin+follow` 降到约 `max(meta+follow, like, coin)`，**通常快 30%~50%**。播放不受影响（本来就在后台），但互动数字出得更快。

### 3. 切换瞬间不再"旧视频还在出声"

旧版点推荐后，要等新地址返回（几百毫秒）才开始换流，这段时间**旧视频还在播、还有声音**，观感就是"新视频加载中、旧视频还在响"。

v4.8 在 `switchVideo()` 里立即：

```java
releaseAudio();                              // 停掉独立音轨
try { if (video != null) video.pause(); } catch (...) { }   // 停画面
playLoadMsg = "正在切换…";                    // 加载层文案
```

加载层同时改为"正在切换…"，与"正在加载喵~"区分开。

### 4. 连点不再串台（竞态收尾）

三个异步回调统一加了归属校验，旧视频晚返回的结果一律丢弃：

```java
if (!bvF.equals(bvid)) return;        // 播放结果
if (!bv.equals(bvid)) return;         // 元数据
if (!currentBv.equals(bvid)) return;  // 推荐列表
```

这样连续快速点 3~4 条推荐，最终稳定停在**最后点的那条**，不会被前面慢返回的结果覆盖。

### 5. 顺带确认：这几处本来就没问题

| 检查项 | 结论 |
|---|---|
| 解码能力查询 `codecPlayable` | 已有 static 缓存，不会每条轨道都新建 MediaCodecList |
| 弹幕 XML 解析 | 已在后台线程，几 MB 也不卡 UI |
| 本地代理选线 | 本来就是 4 条并行竞速取最快，无需改 |
| WBI 签名密钥 | 进程内已缓存，冷启动只请求一次 nav |

> 说明：网络本身的往返时间无法用代码消除（你说排除网络原因，所以我把能省的**请求次数**和**本地串行等待**都省掉了）。切换路径现在是：cid 直接可用 → 一次 playurl → setVideoPath → 代理竞速起流。

## 二、弹幕样式自定义（新功能）

### 入口：长按「弹」按钮

```
点击「弹」= 开关弹幕（原逻辑不变）
长按「弹」= 打开样式面板（新增）
```

首次开启弹幕时，Toast 会提示："弹幕已开启（长按「弹」调颜色/字号）"。

### 可调项

| 项目 | 选项 |
|---|---|
| **颜色** | 原色 / 白 / 黄 / 粉 / 蓝 / 绿 / 紫 / 橙 |
| **不透明度** | 淡(30%) / 中(55%) / 较浓(80%) / 不透明(100%) |
| **字号** | 小(80%) / 标准(100%) / 大(130%) |

- **「原色」是第一个彩色圆点**：选它 = 保留 B 站原生彩色弹幕（红色 SC、黄色高亮等各按弹幕自带颜色显示）
- 选固定颜色后，**所有弹幕统一用该色**，适合白底画面看不清的情况
- 底部有「恢复默认」一键还原

### 实现

- `DanmakuView.setStyle(color, alphaPct, sizePct)`
- 字号变化时自动重算轨道数（`lastHeight=-1` + 清空活动弹幕），不会出现新旧字号重叠
- 设置持久化在 `Prefs`：`dm_color` / `dm_alpha` / `dm_size`，下次进任何视频都生效

## 四、怎么测

**切换速度**：找一个热门的视频，连续点底部推荐的 4~5 条。
- 预期：每条都能在 1~1.5 秒内出画面（网络正常前提下）
- 切换瞬间不应该再听到上一个视频的声音

**弹幕样式**：长按「弹」→ 选「粉」+「大」+「较浓」→ 观察弹幕变成粉色大字；再选「原色」恢复 B 站原生彩色。

**连点不串台**：快速连点 3 条不同推荐，最后应停在你最后点的那条，标题/UP主与画面一致。

## 五、若切换仍超过 2 秒

日志在 `Android/data/com.bixiaoqu.app/files/boot.txt`，重点看这几行：

```
[proxy] 竞速胜出 <host>          ← 代理选线耗时
[dash] 高清流不可用：...          ← DASH 是否降级
[play] audio start @v=..ms       ← 起播时刻
```

把切换前后那一段发我，我能判断是 playurl 慢、代理选线慢，还是解码器初始化慢——这三种的优化手段完全不同。
