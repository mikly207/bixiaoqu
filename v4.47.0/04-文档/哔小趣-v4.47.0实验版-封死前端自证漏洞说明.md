# 哔小趣 v4.47.0 实验版 · 封死「没捐款点一下就能登录」

> **这是 v4.46 引入的漏洞，本版已彻底修复。**
> 现象：不捐款，只点一下「我已支付，申请开通」按钮，就能登录并解锁全部功能。

---

## 一、我必须认领这个错误

v4.45 修好了「前端自证支付成功」的漏洞，但 v4.46 我为了解决「用户要填服务端配置」的问题，
**引入了一条本地置成功的后门**，等于把刚修好的漏洞又打开了。

这就是典型的：为了修 A 而制造 B，而 B 比 A 更严重。

**根本原因**：v4.46 的「宽松模式」在作者未部署服务端时，走的是
「点按钮 → 写本地凭证 → 直接放行」——和 v4.44 那个漏洞在本质上完全一样。

---

## 二、修复方式：把后门整条删掉

不是打补丁，是**删除**。本版客户端**不存在任何本地置成功的路径**：

| 项目 | v4.46（有漏洞） | v4.47（当前） |
|---|---|---|
| 点「我已支付，申请开通」 | 写本地凭证 → 立即解锁 | 只向服务端查询，**服务端没核销就是没付** |
| 宽松模式（relaxedMode） | 存在 | **已删除** |
| 老宽松凭证迁移逻辑 | 存在 | **已删除** |
| 本地写凭证的入口 | 捐赠页 + 迁移函数 | **只剩服务端验签通过后那一处** |
| 未配置服务端时 | 自助开通（假） | **不放行**，并提示联系作者（不引导白付钱） |

判定只剩一条路径：

```
服务端核销 → 服务端 RSA 私钥签名 → App 内置公钥验签通过 → 才算已开通
```

## 三、顺手堵掉一个更隐蔽的漏洞

修完后我做真实场景验证时，发现**还有一个洞**：

服务端对**未支付**的订单同样会签发凭证（`paid=0`）。这个凭证签名是真的、
字段也自洽，原来的 `isTrusted()` 只验签不检查 `paid` 位 → **未付款也能被判为已开通**。

修复只需一行：

```java
if (!st.paid) return false;   // 凭证必须是「已支付」状态
```

这一行已加进 `isTrusted()`，并有专门的单测与守卫断言盯着它，防止以后被删掉。

## 四、真实场景验证（对着跑起来的服务端）

```
-- 场景1：没付款点按钮 --
  ✓ 系统生成订单号
  ✓ 服务端返回未支付
  ✓ 【核心】没付款 → isUnlocked=false → 进不去

-- 场景2：伪造本地凭证 --
  ✓ 随便编签名 → 不放行
  ✓ 自签凭证（用服务端公钥验）→ 不放行
  ✓ 篡改 paid → 不放行
  ✓ 用服务端公钥验自签凭证 → 不放行（公钥锚定生效）

-- 场景3：核销后才能登录 --
  ✓ 作者核销成功
  ✓ 服务端返回已支付
  ✓ 【核心】核销后 → isUnlocked=true → 能登录
```

**10 项全通过**，用的就是 App 源码里真实的 `DonateApi`（真实验签）+ 真实 HTTP。

## 五、作者需要做的事（重要）

因为漏洞已封死，**App 内必须内置服务端地址与公钥**，否则用户无法通过核验。

```bash
cd 哔小趣-捐赠校验服务
bash 一键部署打包.sh https://你的域名      # 生成密钥 + 写入内置配置 + 出双 APK
ADMIN_TOKEN=你的强口令 node server.js      # 启动服务
```

之后打开 `https://你的域名/admin` 核对到账、点「核销」，用户那边约 3 秒内自动开通。

> **给已经用 v4.46 发出去的用户**：他们那份 APK 里的宽松凭证现在一律失效，
> 需要你用新版 APK 重新分发，或在后台核销后重新出包。
