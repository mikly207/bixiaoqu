# 哔小趣 v4.22.0 · 相关推荐「慢一拍」修复 + 加载链路优化

> 版本：4.22.0（versionCode 122）｜平板版 + 手机版｜纯 Java / API 22 / 无 androidx
> 产物：`哔小趣-v4.22.0-平板版.apk`、`哔小趣-v4.22.0-手机版.apk`

---

## 一、先说结论

**「相关推荐总慢一拍」不是一个性能问题，是一个排队问题。**

v4.20.0 为了保首帧，把所有「非首帧必需」的请求都塞进了起播保护窗口（`guardStartup`），
相关推荐也在里面。于是每次进播放页 / 每次换片，推荐都要走这条时间线：

```
点开 → 首帧出画（≈1.8s）→ 再等 1.2s 保护期 → 才发 related 请求（≈0.4s）→ 上屏
                                                        合计 ≈ 3.4s
```

而 `related` 只是几百字节的 JSON，抢不走多少带宽。把它排到首帧后面，
换来的首帧收益几乎为零，代价却是右栏空 3 秒。

v4.22.0 把它拆开了：

| 请求 | 旧版 | 新版 |
|---|---|---|
| 相关推荐 JSON（几百字节） | 首帧后 1.2s 才发 | **点开 30ms 后立刻发** |
| 推荐封面图（几十 KB/张） | 同上 | 首帧后（`prefetchCovers`，仍让路） |
| 推荐 playurl 预取 | 首帧后 1.2s + 500ms | 首帧后 1.2s + **260ms** |
| 首片预热（96KB） | 无 | 首帧后，只给第 1 条 |

推荐上屏：**≈3.4s → ≈0.43s**；同一个视频二次进入（命中内存缓存）**< 50ms**。

## 二、慢一拍的三层原因（都已修）

### 1. 请求被排队（主因）

`loadRec()` 原来长这样：

```java
void loadRec() {
    guardStartup("rec", new Runnable() { ... loadRecNow(); });
}
```

现在：

```java
void loadRec() {
    ui.postDelayed(() -> loadRecNow(), 30);   // 只让出 30ms 给起播请求先出队
}
```

30ms 的作用是让 `play()` 里的 playurl 请求先发出去（同一条 TCP 通道上先来后到），
而不是把推荐真正推迟。

### 2. 没有缓存，每次换片都从零请求

新增 `BiliApi.REC_CACHE`：LRU 48 条 bvid / 5 分钟。

- 同一视频返回播放页 → 秒填
- 「点推荐 → 返回 → 再点回去」→ 秒填
- 换片 → 先查新视频有没有缓存，有就直接换，没有才发网络

### 3. 换片后根本不刷新右栏

旧代码 `switchVideo()` 末尾明确写着「不再重拉推荐列表」，理由是竖屏刷流看不到。
但横屏分屏下右栏一直是可见的 —— 用户点完一条推荐，右栏还挂着上一批（里面甚至还有
刚看完的那条），观感就是「没更新 / 慢一拍」。

现在：`if (!swipeMode) loadRec();`（竖屏刷流仍然不重拉，省带宽）。

### 4. 顺手补了「骨感」

首次进入、且没有缓存时，先铺 6 条「正在加载推荐…」占位行。
换片时如果列表里还是上一个视频的内容，也替换成骨架 —— 用户明确知道在加载，
而不是盯着上一条视频的推荐发呆。

### 为什么不上 ExoPlayer

不是不想用，是**这个工程的构建方式和它不兼容**：

1. 本项目是 `javac → d8 → aapt2 → apksigner` 手工链路，没有 Gradle、没有 androidx。
   media3 依赖 `androidx.annotation`、`androidx.core`、`guava`、`kotlin-stdlib` 等十几个 AAR，
   还要做资源合并与 `proguard` 规则，等于把整个构建链重写一遍。
2. media3 是 Kotlin 写的，dex 体积至少 +2.5MB，冷启动和安装包都会明显变大。
3. **最关键**：ExoPlayer 最终也是调 `MediaCodec` 硬解，和系统 `MediaPlayer` 走的是同一套
   硬解码器。用户感知的「慢」发生在这三处 —— 取播放地址、选 CDN 线路、等首片回源，
   全都在网络侧，换播放器一分钱都省不下来。

所以我们把力气花在等效的地方：**代理层多线路竞速 + 首片预热 + playurl 预取 + 解码器即时释放**。
这四件事才是真正决定「点下去多久出画」的。

### 为什么不切 HLS

B 站 HLS 的码率档普遍低于 DASH，而且要额外拉一次 `m3u8` 才能拿到分片列表 ——
等于多一次网络往返，起播只会更慢。现有 DASH + fMP4 已经是最优解。

### 为什么拿不到 HTTP/2

Android 平台自带的 `HttpURLConnection`（OkHttp 2.x 派生）**只支持 HTTP/1.1**，
要 HTTP/2 必须引入 OkHttp 3.14+ 或 Cronet，同样要动构建链和体积。
实际收益也有限：B 站 CDN 的分片响应本来就是大块传输，HTTP/1.1 的 keep-alive
在代理层已经是「一条连接连续拉多个分片」，多路复用带来的提升可以忽略。

## 四、本轮改了什么（文件级）

### 新增

| 文件 | 作用 |
|---|---|
| `StartupDiag.java` | 起播诊断：区分「网络拉得慢」和「硬件解不动」，并给出自适应档位 |
| `DiskCache.java` | 分片磁盘缓存：400MB / 单文件 48MB / LRU / 原子落盘 |

### 修改

| 文件 | 改动 |
|---|---|
| `PlayActivity.java` | 推荐直发 + 缓存 + 骨架 + 换片刷新；首片预热参数；`chooseHeight()` 弱网限档；起播三处打点；退出时反射释放解码器 |
| `BiliApi.java` | `REC_CACHE`（LRU 48/5min）；`warmFirstChunk()` 96KB 预热；`WARM_POOL`（单线程、低优先级）；`prefetchPlayurl(..., warm)` |
| `LocalProxy.java` | 快路径⓪ 磁盘缓存命中直接本地回放；边转发边落盘（tee）；记录 Range 结束偏移与后缀请求 |
| `BxqApp.java` | 启动时 `DiskCache.init()` |
| `MainActivity.java` | 首屏 playurl 预取 3→4 条，第 1 条带首片预热 |

### 关键实现细节（容易踩坑的地方）

**磁盘缓存的 key 不能是整条 URL。**
B 站每个分片都带一次性鉴权（`deadline` / `upsig` / `trid`），而且每次取址 host 可能被
调度到另一个镜像机房。用整条 URL 做 key，缓存永远命中不了。改成只取 URL 的 `path`：

```
/upgcxcode/xx/xx/12345/12345-1-30080.m4s
```

里面已经含 cid 与清晰度编号，既稳定又能区分不同视频和不同档位。

**半截文件绝不能命中。**
写盘先落 `.tmp`，只有「转发的字节数 == Content-Length」才 `rename` 提交；
`lookup` 时再校验一次长度。宁可多下一次，也不能把半截数据喂给播放器 ——
那是花屏和「卡死」的直接来源。

**没有取址打点时不能判弱网。**
合流（`durl`）和本地文件路径不经过 `StartupDiag.onFetch()`，如果照旧按总耗时判断，
会被误判成弱网，白白降掉用户选的画质。现在这种情况只记样本、不参与降档决策。

## 五、测试

沙箱里没有 KVM，跑不了真机模拟器。测试是三层：

### 1. 纯逻辑单测（JVM，可重复）

| 套件 | 项数 | 结果 |
|---|---|---|
| `StartupDiagTest` | 32 | ALL PASS |
| `DiskCacheTest` | 27 | ALL PASS |
| `LayoutPolicyTest`（v4.21 回归） | 27 | ALL PASS |
| **合计** | **86** | **ALL PASS** |

覆盖点：

- `classify` 边界：1399/1400、2199/2200、BOTH 三重门槛，取址慢时不重复算解码慢
- `adaptHeight`：全档位 × 带宽组合，含 `want=0`（自动）与带宽未知
- 状态机：连续两次才降、连续两次才恢复、只降不升、「慢-正-慢-正」抖动不触发
- 磁盘缓存：完整写入命中、200/206 头与字节校验、`abort` 半截不命中、
  长度不符不命中、超 48MB 放弃、换镜像 host 仍命中、不同视频不串、LRU 淘汰最旧

### 2. 源码回归守卫（44 项）

```
python3 tools/guard_check.py  →  通过 44 项，失败 0 项
```

其中 v4.22 新增 27 项（从 v4.21 的 17 项扩到 44 项），专门盯住这次改动的「危险写法」：

- 推荐请求不许再回到 `guardStartup`（两版都查）
- 缓存必须校验 `bytes == len` 才提交
- 预取第一条必须带首片预热
- 退出必须 `video.reset()` 兜底（两版都查）
- 骨架行必须能识别「上一个视频的旧推荐」

### 3. 字节码验证（确认改动真的进了 APK）

## 六、已知限制（不藏着）

1. **磁盘缓存对超长视频无效**。单个 m4s 超过 48MB 就放弃缓存。3 分钟内的竖屏视频
   （720P 约 15~30MB）能命中，一小时的长视频不会缓存 —— 否则磁盘会被吃光。
2. **首次播放没有缓存加速**。缓存只在「第二次看同一个视频」时生效，这是物理限制。
3. **自动降码率只降一档**，且要连续两次确认。想强制更高画质，在画质面板手选即可，
   手选后仍会被「网络确实扛不住」限幅，但会有提示。
4. **没有真机回归**。布局状态机、诊断逻辑、缓存语义都做了穷举/边界测试，
   但「某台具体机型解码器抽风」这类问题只能真机暴露。
