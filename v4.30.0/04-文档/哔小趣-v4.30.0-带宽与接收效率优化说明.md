# 哔小趣 v4.30.0 · 让一条视频吃满带宽

> 这一版没有再动界面，全部在网络层：**改并发、改接收、改优先级**。

---

## 一、先定位：不是"带宽不够"，是"一条连接吃不满"

播放器取流走的是 `LocalProxy`（127.0.0.1），它把请求转发给 B 站 CDN。
整条链路上只有一个地方真正决定"快不快"：**代理到 CDN 的那一段**。

而这一段长期只开**一条 TCP**。TCP 有个绕不过去的约束：

```
单连接吞吐 ≈ 接收窗口 / RTT   （带宽时延积 BDP）
```

移动网络 RTT 常在 40~120ms，窗口再大也就那么点 —— 实测单连接通常只跑到
链路带宽的 **40%~60%**。于是出现那种很别扭的现象：

> 同一个 WiFi，网页/其他 App 秒开，这里一直转圈；
> 测速明明有 50Mbps，播放器只有 2MB/s。

**调大缓冲区、提线程优先级，只会让同一条连接跑得更稳，不会让它变宽。**
要变宽只有一条路：多开几条。

## 二、改了什么

### 1. 并行分段拉流（核心）

一条 ≥4MB、上游确认 `206` 的整段请求，现在拆成 **3 段、3 条连接**同时拉：

```
MediaPlayer ──► LocalProxy ──┬─► 段0 [0, 4.0MB)   ─┐
                             ├─► 段1 [4.0, 8.0MB) ─┤ 有界队列 → 主线程按段序写出
                             └─► 段2 [8.0, 末]     ─┘
```

三个关键设计，缺一个就会出事：

| 设计 | 为什么必须有 |
|---|---|
| **有界队列** 4 块 × 128KB | 某段跑得快时不能无限囤数据。队列满 → 该段线程阻塞 → 天然背压，内存恒定 ≈ 1.5MB |
| **严格按段序写出** | 播放器只认连续字节流。段 1 再快也得等段 0 写完，否则就是花屏 |
| **失败即回退** | 任一段异常 / 15s 不吐数据 → 停止并行，返回「已写出的连续字节数」，用单连接从断点续传补齐 |

启用条件刻意保守，任一不满足就走老路径（行为与 v4.29 完全一致）：

```java
okCode == 206                    // 上游真支持 Range（回 200 整包的不拆）
&& !req.suffix                   // bytes=-500 这种末尾请求不拆
&& len >= 4MB                    // 太小的话握手开销吃掉收益
&& 候选线路 >= 2                 // 换不同 host，绕开同资源并发风控
&& 闸门有空位                     // 全局最多 6 条"帮工"连接
```

段 0 直接复用已经握好手的那条连接；段 1/2 优先换 **不同 host**，
因为同一台 CDN 上并发拉同一个文件的多个 Range，有概率被判成异常流量（403）。

### 2. 端口接收效率

| 项 | 旧 | 新 | 影响 |
|---|---|---|---|
| ServerSocket backlog | 32 | **128** | 换片瞬间旧连接没退完、新连接已进来，32 个排队位会把新连接直接拒掉 |
| 回环发送缓冲 | 512KB | **1MB** | 4K 一秒 5~10MB，缓冲小 → `write` 早阻塞 → 上游发送窗口跟着收缩 |
| 读缓冲 | 每请求 `new byte[256KB]` | **线程内复用** | 高码率下每秒几十次大数组分配，全是年轻代 GC |
| 转发线程池 | 4~8 / 队列 48 | **6~12 / 队列 96** | 视频轨 + 音轨 + 预读 + 换片残留会同时占连接 |
| HTTP 连接池上限 | 5（系统默认） | **12** | 并行 3 段 + 音轨 + 预读 > 5，超出的连接会被池子直接关掉重建 —— 每次都是一次多余的握手 |
| 落盘 | 同步，占转发线程 | **异步单线程** | 写文件 / `renameTo` / 目录 `sweep` 不再卡在 read→write 管道上 |

最后一条值得单说：旧版 `DiskCache.Writer.write()` 直接跑在转发线程里，
`commit()` 里还有 `renameTo` + 目录扫描。闪存一抖动，转发循环就停在那儿 ——
用户看到的就是「网速明明够，画面就是不往前走」。现在数据进有界队列，
`proxy-disk` 单线程慢慢写；**队列满就放弃这份缓存，绝不让缓存拖住播放**。

### 3. 网络优先级

Android 没有"每条连接的 QoS"这种 API，能调的只有**线程调度顺序**和**并发数**：

| 线程 | 优先级 | 理由 |
|---|---|---|
| `proxy-seg`（并行段） | NORM+3 | 吞吐主力，排在预读之前 |
| `proxy-io`（转发） | NORM+2 | 用户能感知到的"加载速度"就是这几条线程 |
| `proxy-race`（选路） | NORM+1 | 起播第一环，但只做建连+读头，很快归还 |
| `bxq-prefetch`（取址预取） | NORM+2 | 与转发同级，但只剩几次 JSON 请求 |
| `bxq-warm`（首片预热） | NORM-1 | 给下一条视频省时间，不该抢当前视频的带宽 |
| `proxy-disk`（落盘） | NORM-1 | 可以慢，转发不能等 |

**没有**把任何线程提到 `MAX_PRIORITY`：那会排到 UI 线程前面，
高码率下 128KB 块的拷贝会让滑动掉帧。快，但不能以卡换快。

## 四、预期效果与说明

- **起播**：大 m4s 的首段由 3 条连接并行拉，高 RTT 下通常比单连接快 **1.5~2.5 倍**；
  但首帧也受 moov 索引位置与解码器影响，不会无限制变快。
- **拖动**：`bytes=N-` 同样走并行，缓冲更快填满。
- **小分片（<4MB）**：不拆，行为与之前一致 —— 拆了反而更慢（3 次握手换 1 次）。
- **流量**：不增加总量（同一段数据只是分三条连接取），只在冷启动时多 2 次 TCP/TLS 握手。
- 如果某个 CDN 明确拒绝对同资源分段（403/416），会自动退回单连接，不会比现在更差。
