# 哔小趣 v4.20.0 — 竖屏播放专项提速

> 本次针对「竖屏视频点开后明显比横屏慢」做根因排查与修复。结论：**线路确实被占满了，但不是 CDN 线路不够，而是我们自己一次性发了太多请求把带宽和线程占住了**。

---

## 一、先说结论：慢在哪

我把竖屏路径和横屏路径逐行对比，发现竖屏多走了 4 个横屏完全没有的环节。按影响从大到小：

### 1. 进入竖屏时一次发出 10+ 个请求（主因，就是你说的「线路满溢」）

竖屏视频会进入沉浸式 + 上下滑模式，这个模式一启动就会连带触发：

| 请求 | 大小 | 说明 |
|---|---|---|
| `related` 推荐列表 | 几十 KB | 构建滑动队列 |
| `popular` 热门 ×3 页 | 几十 KB ×3 | 队列不够时连打 3 页 |
| 相邻视频 `playurl` ×6 | 小 | ±3 条，前后各 3 |
| 点赞 / 投币 / 关注状态 ×3 | 小 | 右侧互动栏要显示 |
| 整包弹幕 XML | **几百 KB ~ 几 MB** | 热门视频一条就几 MB |
| 相邻视频封面 | 每张 100~300 KB | 高清海报 |

**这些全部和视频首帧抢同一条链路。** 横屏详情页只发 `playurl + view + 弹幕` 三个，所以横屏显得快 —— 不是横屏优化得好，是竖屏被自己拖住了。

### 2. 详情接口被互动状态 `join` 卡住，最坏多等 5 秒

`loadVideoMeta` 里 `likeState` / `coinState` 用 `join(2500)` 各等 2.5 秒，而**竖屏判定依赖这个接口返回的 `dimension`**。所以弱网时：竖屏判定晚 → 首帧已经出画了才切成全屏 → 整页重排 + 画面容器尺寸突变 → 看起来就是「卡一下才开始播」。

### 3. 列表把宽高比丢掉了，竖屏只能「事后」才知道

首页热门列表的接口其实**同时返回 `cid` 和 `dimension`**（实测确认），但旧代码只取了 `bvid / title / pic`：

- 没有 `cid` → 点开后要串行等一次 `pagelist`（300~800ms）才开始取播址；
- 没有 `dimension` → 播到一半才知道是竖屏，再做一次全屏重排。

热门/关注进入的竖屏视频，这两笔各白等一次。

### 4. 代理一次竞速 6 条线路

竖屏视频的 `playurl` 常给 6 个 `backupUrl`，旧版 6 条 TCP/TLS 同时建连抢同一个文件：移动网络下握手互相拖累，还容易触发 CDN 同资源并发风控（403）。

## 二、这次改了什么

### 起播让路（核心）

新增「起播保护窗口」：从点开到首帧出画 +1.2 秒内，**只允许视频流和音轨两条连接**，其余请求全部排队，窗口一过自动补发。

- 弹幕 XML、推荐列表、热门补充、相邻预取、线路预热、点赞/投币/关注 → 全部进队列
- 队列按「首帧后 1.2 秒」或「6 秒兜底」放行，不会永久卡住
- 首帧一出，立即收敛窗口，不用等满 6 秒

### 竖屏判定前置（三重保险，谁先到用谁）

1. **列表带 `aspect`**：首页推荐 / 热门 / 关注都从 `dimension` 解析后带进播放页
2. **`playurl` 轨道宽高兜底**：`dash.video[0].width/height` 在 `setVideoPath` 之前就有，从搜索/动态/深链进入也能在首帧前判定
3. **`view` 接口**：最后兜底，且不再被互动状态阻塞

判定提前后，布局在**首帧之前**就摆好，不再有「横屏小窗先出来、再跳成竖屏全屏」的二次重排。

### 列表补 `cid`，省一次往返

热门/关注列表的 `cid` 现在一起带过去。列表没带 `cid` 的条目（部分接口确实没有），点击瞬间就预取 `pagelist`，拿到 cid 后立刻链式预取 `playurl`。播放页起来时地址往往已就绪。

### 详情接口不再被互动状态拖住

`loadVideoMeta` 拆成两段：先只取 `view`（标题/封面/尺寸/统计），立刻回填；点赞/投币/关注推到首帧之后，拉到再刷新图标。原来最坏 5 秒的 `join` 彻底去掉。

### 代理竞速 6 条 → 3 条一批

- 首批并发 3 条，够用；全部失败才补下一批 3 条
- 已有胜出者时，未开跑的线路直接放弃，不再建连
- 竞速等待 8s → 4.5s，全不通就快速 502 让播放器立刻重试
- 线路预热 2 条 → 1 条

### 起播海报：把黑屏填掉

进入播放页 / 切视频时，先把列表封面铺满画面（这张图列表刚显示过，ImgLoader 内存里还在，零网络开销），首帧出画后 200ms 淡出。

**首帧就算还是 800ms，用户看到的也是封面而不是黑屏** —— 这是体感上最直接的一刀。加载框延迟也从 3000ms 收到 1300ms。

### 滑动流畅度

- 滑动期间跳过 500ms 的进度回写（`setProgress` + 两个 `setText` 会和位移动画抢主线程）
- 弹幕在真正开始拖动时才隐去并停止推进（v4.19 已做，这次补上 `fadeStartupPoster`，海报不再挡翻页）
- 预取窗口 ±3 → ±2：原来一次排 6 条 `playurl`，闸门只有 2，队列会排到用户已经滑过去

### 标题不再空等

竖屏沉浸式界面出现时，标题直接用列表带过来的填上，不用等详情接口；UP 名/头像随后到位。

### 冷启动第一个视频

新增后台预热设备指纹（`buvid3/buvid4`）。旧版冷启动后第一个 `playurl` 要同步打一次首页拿 Cookie（0.8~2 秒），这就是「第一个视频特别慢、之后正常」的原因。

## 三、改动前后对比（竖屏进入）

| 项目 | v4.19.0 | v4.20.0 |
|---|---|---|
| 首帧前并发请求 | 最多 13 个 | 1~2 个 |
| 首帧前并发 CDN 连接 | 6 条 | 3 条 |
| 竖屏判定时机 | 首帧后（等 view） | 首帧前（列表 aspect / 播址轨道） |
| 详情接口阻塞 | 最坏 join 5s | 不阻塞 |
| 首帧前画面 | 纯黑 | 列表封面 |
| 加载框出现 | 3000ms | 1300ms |

## 四、怎么验证

装好后连点 5 个竖屏视频，看应用日志里 `perf` 这几行（`BiliXQ` tag，或应用私有目录 `boot.txt`）：

```
[perf] 取址 3ms · BV1xx...        ← 预取命中，接近 0
[perf] DASH 首帧 780ms · BV1xx...  ← 点开到出画
```

- 取址接近 0 = 预取链路生效
- 首帧 < 1200ms = 达标（网络正常时）
- 如果取址 500ms+ 且不是首次播放，说明预取没命中，把日志发我

另外重点看三处：
1. 竖屏点开后**不再有「先小窗后跳全屏」**的闪动
2. 首帧前看到的是封面，不是黑屏
3. 连滑 10 条是否还掉帧

## 五、还没有做的（避免过度改动）

- **TextureView 换成「滑动截图」**：抖音式滑动时把视频换成静态截图，位移结束再切回视频。能再省一大截合成开销，但要处理截图与视频切换的时序，风险高，这次没上。
- **滑动期间给覆盖层加硬件缓存层**：理论上能减少整屏文字重绘，但低端机可能因纹理内存出现黑块，先观察这次的效果。
- 搜索/收藏/动态等低频入口的列表还没带 `aspect`（接口大多不返回 `dimension`），这些入口会走「播址轨道宽高」兜底，仍比旧版快，但不如首页。
