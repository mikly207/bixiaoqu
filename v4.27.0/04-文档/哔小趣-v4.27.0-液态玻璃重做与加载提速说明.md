## 一、删除控制条上下贯穿边线（核心诉求）

### 问题定位

用户反馈「控制条上下有两条贯穿的边线，整体像一块板，没有一体感」。
截图实测（1dp = 3px）确认：**上边线**与**下边线**都是横贯整个控制条宽度的硬线。

在代码里找到**三处叠加**共同造成这个现象：

| # | 代码位置 | 作用 | 问题 |
|---|---|---|---|
| ① | `shRim` 边缘高光 | 垂直渐变 `上 0xC4 → 下 0x1A`，整圈描边 | 上边被**整条**打亮成一条 0xC4 的横线 |
| ② | `shTopSpec` 顶面镜面带 | 横贯全宽的细亮条 | **第二条**上边线 |
| ③ | `shFootL` 底缘反光 + `shBottom` 底部暗部 | 下沿整条托亮 | 一条贯穿的**下边线** |

三条水平长线一夹，控制条立刻从「一层玻璃」变成「贴在画面上的一块板」。

### 解决思路：把光学从「上下」转到「左右端面」

真实玻璃横条（iOS 液态玻璃 / visionOS）的光学分布恰恰相反：

- **长边中段**：几乎没有反射，画面直接透过玻璃看过去 → 玻璃与画面的边界是「化开」的，这就是**一体感**的物理来源；
- **左右端面**：光线在玻璃–空气界面发生全反射，出现一条很亮的窄带，外侧镶一道暗边（厚度），再往外是冷暖色散。

于是把**所有线状光学的渐变方向一律从「垂直」改成「水平」**：

```java
// 旧：垂直（上强下弱）—— 造成上下贯穿线
shRim = new LinearGradient(0, 0, 0, h, 0xC4FFFFFF, 0x1AFFFFFF, CLAMP);

// 新：水平（两端亮、中段完全透明）—— 长边无任何贯穿线
shRim = new LinearGradient(0, 0, w, 0,
        new int[]{0xE6FFFFFF, 0x2EFFFFFF, 0x00FFFFFF, 0x2EFFFFFF, 0xE6FFFFFF},
        new float[]{0f, 0.09f, 0.5f, 0.91f, 1f}, CLAMP);
```

改动的 8 个渐变全部转为水平：`shFill`（基底压暗）、`shRim`（端面高光）、
`shInner`（厚度暗线）、`shInner2`（内表面反射）、`shTopSpec`（顶棱镜面）、
`shCaustic`（底部焦散）、`shDisp`（边缘色散）、`shBottom`（接地暗影）。

同时把**贯穿全宽**的几笔改为**只画左右两段**：

- 顶棱镜面 → 只在左右端各一段（`endSpan = min(w*0.20, r*2.4)`）
- 底部焦散 → 只在左右端各一段
- 底缘反光 → 只在左右端各一段

### 像素级量化验证

在长边中段做垂直亮度剖面，测「上/下沿相对条形内部的亮度跃升」（跃升越大＝边线越明显）：

| 指标 | 旧版 v4.26.0 | 新版 v4.27.0 | 变化 |
|---|---|---|---|
| **上边线跃升** | +72.5 | **+26.5** | **−63%** |
| **下边线跃升** | +111.9 | **−2.5** | **−102%（彻底消失）** |
| 端面−中段亮度差 | +1.1 | **+16.3** | **×15（玻璃感来源）** |

旧版端面差仅 1.1 —— 说明光学是均匀铺开的，根本没有「端面」概念；
新版 16.3，光学真正集中到了左右端头。

## 二、边框进一步收窄

旧版多层描边叠加后接近 **2dp 厚** —— 那正是塑料边框的观感。
v4.27.0 把每一层都压薄：

| 描边层 | v4.26.0 | v4.27.0 | 收窄 |
|---|---|---|---|
| 边缘高光 `shRim` | 1.3dp | **0.85dp** | −35% |
| 厚度暗线 `shInner` | 1.1dp | **0.70dp** | −36% |
| 内表面反射 `shInner2` | 0.55dp | **0.42dp** | −24% |
| 边缘色散 `shDisp` | 0.9dp | **0.60dp** | −33% |
| 顶棱镜面 `shTopSpec` | 0.7dp | **0.55dp** | −21% |
| 圆钮边缘 `pEdge` | 1.2dp | **0.75dp** | −38% |
| **多层叠加总厚** | **≈2.0dp** | **≈1.1dp** | **−45%** |

层次全部保留（三层厚度结构不变），但不再有「厚边框」。

## 三、进一步去除塑料感

| 项 | v4.26.0 | v4.27.0 | 理由 |
|---|---|---|---|
| 乳白雾（身体） | 0x08 → 0x03 | **0x06 → 0x02** | 身体越透，底下画面越干净 |
| 噪点颗粒 alpha | 12 / 8 | **8 / 5** | 细磨砂，不是砂纸 |
| 顶部受光 | 0x14，覆盖 45% 高 | **0x0A，覆盖 30% 高** | 铺太高会连成上边线 |
| 基底压暗 | 垂直（下沿更实） | **水平（两端实、中段透）** | 厚度感来自端面，不是整片发暗 |
| 接触阴影 | 0x22 / 0x0E / 0x05 | **0x1A / 0x0A / 0x04** | 影子越淡越散，越不像贴纸 |
| 圆钮底缘聚暗 | 0x24 | **0x14** | 原来那圈暗把圆钮下半圈「坐」在地上，像实心按钮 |

**圆钮特别改造**：圆形没有长边可依托，若沿用垂直渐变，下半圈会剩一道明显暗弧，
整颗圆钮看上去像「半截描边」。改为**左上角径向衰减** —— 高光绕左上走一圈，
到右下方彻底消失，形状全靠光学撑住。

## 四、视频加载速度优化

### 修复一个致命 Bug：预热链路 100% 失效

```java
// 旧版 warmupOne —— key 用 qualityQn(q)（自动档 = 120 / 1080P = 80 …）
String ck = BiliApi.urlCacheKey(it.bvid, it.cid, qn);

// 而所有预取入口写入缓存用的都是 QN_ALL（= 0）
BiliApi.prefetchPlayurl(it.bvid, it.cid, BiliApi.QN_ALL, ...);
```

```
预取写入 key = "BVxxx|123|0"
warmupOne 查 key = "BVxxx|123|120"   ← 永远对不上
```

**两个 key 永远不匹配 → `takeUrlCache` 恒为 null → 线路亲和预热从未执行过。**

后果很直接：`LINE_AFFINITY` 里从来没有相邻视频的亲和线路，
用户每次滑到下一条，代理都只能走「全量竞速」—— 3 条线路并行建连、读头、择快，
每次滑动起播都白白多花几百毫秒。
现在统一用 `QN_ALL` 取址，亲和线路才真正能命中。

### 其余五项提速

| # | 优化 | 说明 |
|---|---|---|
| 1 | **首片预热与正式播放同轨** | 旧版固定预热 `dash.video[0]`（码率最高那条，通常 4K），但用户设置常是 1080P —— URL 和 CDN host 都对不上，预热全白做还白占带宽。改用 `pickVideo(playData, targetH)`，与正式播放走**同一条选轨逻辑** |
| 2 | **新增音频轨首片预热** | DASH 音视频分离是两条独立 HTTP 流。音频在画面首帧之后才 prepare，此前毫无预热 → 声音迟到半秒。现在一并预热，音画同步更准 |
| 3 | **滑动相邻条目拉首片** | 连滑时手指落下到首帧只有 1~2 秒，只预取地址的话起播还要从零建连 + 冷启动 TLS。现在紧邻条目（step==1）提前拉 96KB 首片，起播只剩「解码」 |
| 4 | **竞速错峰收紧 16ms → 8ms** | 竞速窗口内每条线路都要 DNS + TCP + TLS 三次往返（移动网络 100~300ms），错峰每多 8ms 首帧就晚 8ms。风控敏感点在「瞬时并发数」而非毫秒级时差 |
| 5 | **预热连接入池可复用** | 旧版预热完立刻 `disconnect()`，把刚握好的 DNS/TCP/TLS 成果亲手掐掉。改为读完 1KB 后正常关闭响应流、**不调 disconnect**，JVM keep-alive 池会保留这条连接，正式起播同 host 直接复用，省掉整段握手 |
