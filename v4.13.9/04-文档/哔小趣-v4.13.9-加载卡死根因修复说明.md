## 一、之前为什么一直没修好

前几版我一直在改「线程池 / 并发闸门 / 预热读 / 超时」，方向错了。这次我用真实线路做了穿透代理的实测，才定位到真正的元凶。

**决定性证据**（用真实 DASH 8 条线路穿透本地代理拉流）：

| 测试 | 结果 |
|------|------|
| 单条线路直连 CDN | 206 正常 ✅ |
| 8 条线路并发穿透旧版代理 | 多数返回 **403 HTML 错误页**，偶尔 206 ❌ |
| 修复后 8 条线路并发 | **10/10 全部 206**，响应体是真实 `ftyp` MP4 数据 ✅ |

## 二、真正的根因

B 站 CDN 对**同一资源、同一时刻、从多个不同节点并发请求**有风控：会抢先返回 **403 拦截页**（HTML），而不是视频数据。

而代理的线路竞速代码里写的是：

```java
if (code >= 500) throw new Exception(...);  // 只把 5xx 当失败！
```

**403 是 4xx，没被判失败** —— 于是那条最快的 403 响应被当成"竞速胜出"，代理把 403 HTML 页面**原样转发给播放器**。MediaPlayer 收到的是一段 HTML 而不是视频，自然永远解不出画面，就一直转圈「加载中喵~」。

- 偶尔竞速到正常线路 → 能播（这就是用户说的"**有概率**"）；
- 门槛更低的清晰度（720P）线路调度更集中，更容易踩到 403 → "连 720P 都加载不出来"。

## 三、修复内容

1. **竞速判定只认 2xx**（核心）：`code < 200 || code >= 300` 一律判该线路失败，403/412/404/301 等不再可能被当成胜出；继续等其他真正吐视频的线路。
2. **错峰竞速**：多条线路按序号错开 25ms 依次发起，避免"同资源瞬时并发"直接触发 CDN 风控；首条仍立即发出，不影响起播速度。
3. **响应状态行加固**：胜出连接统一按 200/206 回复播放器，杜绝异常状态码污染（旧版甚至出现过 `HTTP/1.1 403 OK` 这种畸形响应头）。

## 四、验证结果
