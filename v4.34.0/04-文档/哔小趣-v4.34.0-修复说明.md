# 哔小趣 v4.34.0 · 修复说明

> 版本号 `134` / `4.34.0`（平板版、手机版 × 原版 UI、iOS UI 共四个包）
> 签名与上一版相同，可直接覆盖安装。

本轮针对反馈的四类问题逐项修复，外加一轮全工程漏洞自查。**共修掉 6 个真实缺陷**，其中两个是「一直存在但从未生效」的隐性 bug。

## 一、动态页点左栏头像闪退（致命）

### 现象
动态页「关注」流左侧是 UP 主头像列，**点任意一个头像 App 直接闪退**（无崩溃弹窗，窗口收缩后回到桌面）。

### 根因
`DynFeedView.applySideStyle()` 里这一行：

```java
ImageView av = (ImageView) ((LinearLayout) cell.getChildAt(0)).getChildAt(0);
```

左栏每一格的第 0 个子 View 是 `avBox` —— 一个 **FrameLayout**（头像 + 描边层），不是 `LinearLayout`。这行强转在运行时会抛 `ClassCastException`。

之所以平时看不出来，是因为它踩在**两条不同的调用路径**上：

| 路径 | 有没有 try 保护 | 结果 |
|---|---|---|
| 渲染左栏 `renderSide()` | **有**（`try { renderSide(list); } catch`） | 异常被吞掉 → 头像照常显示（`addView` 在 `applySideStyle` 之前已经执行）→ 平时完全看不出问题 |
| 点头像 `setFilter()` | **没有** | 主线程抛异常 → 进程退出 → 闪退 |

换句话说：**这条代码一直在崩，只是崩在没人看的角落里；一旦用户点它，就炸。**

### 修法
- 所有强转改成「先判类型、再取子视图」（`ViewGroup` + `instanceof`），任何一步不符合预期就跳过这一格；
- `setFilter()` 加异常兜底 —— 筛选是纯交互增强，失败时退化成「保持原样」，绝不能连带闪退；
- 顺手修了一个小 bug：再点同一个头像取消筛选时，`filterName` 没清空，标题会一直显示上一个 UP 主的名字。

## 二、1080p 音画不同步 / 卡顿（老设备与各机型）

### 为什么老设备上更容易出问题
DASH 是音视频分离的两条流：画面走 `VideoView`（`MediaPlayer`），声音走另一个 `MediaPlayer`。两个播放器的时钟天然独立。

- 音频轨很轻，永远先到、永远在跑；
- 视频轨重（1080p），网络抖动或解码跟不上时**缓冲耗尽会停住**（`position` 不前进）；
- 于是「画面卡住、声音继续往前」= 用户听到的**音画不同步**。

### 旧版对策的三个问题
```java
if (now - lastAudioSync < 2500) return;          // ① 2.5 秒才比一次
if (Math.abs(aPos - vPos) > 500) audioPlayer.seekTo(vPos);   // ② 阈值 500ms
```
- 阈值 500ms：人耳在 200ms 以上就能察觉，这段时间用户一直听着不同步；
- 频率 2.5 秒：两次校正之间漂移能跑到 3 秒；
- **用 seek 纠偏**：音频流 seek 会整段重新缓冲，老设备上就是一次卡顿 → 卡顿 → 漂移 → 再 seek → 更卡的恶性循环。

### 新策略（三档 + 冻结）
| 漂移量 | 动作 | 理由 |
|---|---|---|
| ≤ 200ms | 不动 | 听不出来，动它只会引入新抖动 |
| < 550ms | 微调音频速率 ±3% / ±6% **渐进**拉回，**绝不 seek** | 渐进无感，seek 有代价 |
| ≥ 550ms | 硬对齐（seek） | 到了这个量渐进追不上，必须一步到位 |

外加**画面卡住时冻结音频**：检测到连续两次采样（>1 秒）画面位置几乎不动，就先把声音冻住；等画面恢复前进，再把音频 seek 到画面位置一起续上。老设备（解码跟不上）与弱网（缓冲耗尽）两种成因都能兜住 —— 用户至少不会听到「声音一直往前跑、画面不动」。

> 校正频率 2500ms → **700ms**。变速只在速率真的需要变化时才动，避免频繁 `setPlaybackParams` 造成音频杂音。

### 老设备自动降档
新增 `DeviceTier`（按系统版本 / 内存 / CPU 核心数 / 有无 AVC 硬解分级）：

| 等级 | 判定 | 清晰度上限 | 并行段数 |
|---|---|---|---|
| 低端 | ≤1.5G 内存 / 四核 / Android 5.x / 无硬解 | 480p | **1 段**（不并行） |
| 中端 | 2~3G 内存 / 老系统 | 720p | 2 段 |
| 高端 | 6G+ 内存 / 8 核 / 新系统 | 不限制 | 3 段 |

并行段数也一起降的原因：**并行拉流是用多开连接换吞吐的**，只在网络和 CPU 都跟得上时成立。老设备上 3 条连接 = 3 个线程 + 3 个 socket + 3 份 TLS 状态，CPU 先被吃光，表现反而是「越并行越卡」。

**用户手动选过画质之后就不再自动降档** —— 明确选了 1080p 就给 1080p，只提示一次，由用户自己改回。

## 三、切到别的 App 再回来，视频重新播放

### 根因
系统的 `VideoView` 在 Surface 被销毁（Activity 不可见）时，会把内部 `MediaPlayer` **release 掉**；回到前台重建 Surface 后，它会**从头** `openVideo()`。用户看到的正是「切出去再回来，视频从头播」。

原来的续播机制只有 `onDetachedFromWindow` 一条触发路径 —— 而切后台时视图**不会被摘下**，所以位置从来没能被记下来。

### 修法
1. `onPause` 主动保存位置到 `resumePos` + `bgResumePos`，并记下当时是否在播；
2. `onStart` 分两种情况恢复：
   - **Surface 被重建** → 新的 `onPrepared` 会自动 `seekTo(resumePos)`（原有机制接上了），另外再补一层「位置还没回位就再 seek 一次」的重试（最多 5 次 × 280ms）；
   - **Surface 还在**（只是不可见）→ 视频停在暂停态，这里负责续上；
3. **用户本来就是暂停的** → 用 `bgPausePending` 标记，回来后不会自己播起来（重建后的 `onPrepared` 默认会 `start()`）；
4. 「后台播放」开关打开时行为不变（继续出声 + 通知栏控制）。

## 四、平板横屏加载慢 · 端口 · 网络优先级

### 4.1 一个从未生效的连接复用（重要）
`v4.31.0` 声称做了「读干净就回池复用」，但**精确亲和路径的 `finally` 里无条件 `disconnect()`**，把成果亲手掐掉了：

```java
serveWinner(s, hit, u, req);   // 内部已经判断过「读干净就别断开」
return;
} finally {
    if (hit != null) { hit.disconnect(); }   // ← 这里又断开了
}
```

而这条路径正是**同一视频后续分片的主路径** —— 一个 DASH 视频几十个分片全走它。结果就是几十次 DNS + TCP + TLS，滑到下一条时这些握手正好叠在起播等待里。**这个连接复用在最热的地方从来没生效过。**

现��只在「没交给 `serveWinner`」时才断开。

### 4.2 跨视频 host 亲和（换片不用重新竞速线路）
线路亲和的 key 是 `host + path`，**换个视频 path 就变了** → 首片又要 3 条线路重新竞速，每条一次 DNS+TCP+TLS（移动网络 100~300ms）。

但 upos 的 host 本身在不同视频之间是通用的 —— 鉴权全在 URL 的 query 里，host 不带视频相关参数。于是新增 `GLOBAL_HOST`：记住最近验证过能用的 host，换片时先单连直连它。

> 命中 → 约 50~150ms；原来 3 条竞速 → 约 300~900ms。**平板横屏连点推荐的首帧提前 200~400ms。**
> 命中失效（403 / 超时）自动回落全量竞速，没有风险。

### 4.3 线程调度：之前的「优先级」全是无效代码
全工程 **16 处** `Thread.setPriority(...)`，注释还写着「优先级保持 NORM+2 让起播取址优先拿到 CPU」——

**Android 的 ART 根本不理会 Java 层的 `Thread.setPriority()`**。Java 规范里的 1~10 在 Android 上只是一个被记下来的数字，调度器完全不看它。真正决定线程先后的是 Linux nice 值 + cgroup 分组，只能通过 `Process.setThreadPriority()` 改。

也就是说：**所谓「网络线程调度调不动」，根子就在这里** —— 视频分段、封面下载、落盘、日志在调度器眼里完全平级，谁的代码碰巧先占住 CPU 谁就赢。

新增 `NetPrio` 统一改用真正生效的优先级，并用**相对关系**表达诉求（而不是把某个线程抬到离谱的高，那会反过来把 UI 挤掉，低端机更卡）：

| 线程 | 优先级 | 说明 |
|---|---|---|
| 视频分段 · 代理转发 · 线路竞速 · 起播取址 | `FOREGROUND` (-4) | 播放主链路，永远先跑 |
| 封面（可见项） | `DEFAULT` (0) | 与改造前一致，不让用户感到变慢 |
| 封面预取 · 落盘 · 首片预热 | `BACKGROUND` (10) | 明确给视频让路 |
| 日志 · 后台清理 | `LOWEST` (19) | 永远不参与抢 |

### 4.4 其它
- 冷启动 DNS 预解析扩到实际会用到的域名：`upos-sz-mirrorcos` / `mirrorali` / `mirrors3` / `mirror08c` + `i0/i1/i2.hdslb.com`（原来只预解析了一个 CDN 域名，其它线路的域名没解析过，正式起播要白等 50~200ms）；
- 代理并行段数改为按设备能力动态设定（见上表）；
- 代理 `backlog 256` / 接收缓冲 1MB / IO 线程 8~16 / `TCP_NODELAY` 保持不变。

## 五、程序漏洞自查

除了上面这些，另外修掉：

1. **`AccentActivity` 取色页** —— `(TextView) row.getChildAt(2)` 强转，改为先判类型再取；
2. **`GameActivity.closeGame()`** —— `(FrameLayout) stage.getParent()` 在 parent 为 null 时会 NPE（Activity 销毁 / 布局重建路径），改为先判类型；
3. **`PlayActivity` 的跨线程字段可见性** —— `bvid` / `curBv` / `curCid` 是非 volatile 字段，却由主线程写、播放任务与推荐任务在后台线程读。Java 内存模型下工作线程可能永远读到旧值，后果是「切了视频，旧视频的回调反而能通过 bvid 校验、把新视频顶掉」。已全部加 `volatile`；
4. 复查了全工程的静态集合边界、Handler 泄漏、socket 关闭路径、缓存上限、`getChildAt` 越界风险 —— 未发现新的无界增长或资源泄漏（`PAGES_CACHE` 有 64 项上限、`REC_CACHE` LRU 48 项、`URL_WARMED` 512 项）。

## 七、一个已知边界

**兼容（合流）解码模式**下声音与画面在同一个播放器里，个别机型锁屏销毁 Surface 时可能一起停，切回默认解码（DASH 双流）后台最稳。

另外，用户手动选过画质后老设备不再自动降档 —— 这是尊重用户意愿的取舍；如果希望强制按设备能力压制，可以在「画质」里手动选低档。
