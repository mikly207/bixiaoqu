## 二、全屏键为什么会被挤出去（根因）

### 实测数字

手机 360dp 宽的屏幕上：

```
屏幕宽            360dp
− 页面左右边距     20dp   (10 + 10)
= 控制条可用       340dp
− 玻璃板内边距     22dp   (11 + 11)
= rowTools 可用    318dp   ← 真正能放控件的地方
```

而 v4.24.0 的控制条内容**实需 352dp**：

| 控件 | 宽度 | 间距 | 合计 |
|---|---|---|---|
| 播放 | 28 | 9 | 37 |
| 时间 | 88 | 10 | 98 |
| 弹幕开关 | 28 | 5 | 33 |
| 选集 | 42 | 5 | 47 |
| 倍速 | 77 | 5 | 82 |
| 更多 | 24 | 7 | 31 |
| 全屏 | 24 | — | 24 |
| | | | **352** |

**溢出 34dp。**

### 为什么会「看得见却按不到」

`LinearLayout` 放不下时有个很讨厌的行为：它**不会裁掉最后一个子 View**，而是把它排到容器右边界之外。
于是「更多」压出玻璃板右缘，「全屏」被推到屏幕外，只剩半个 —— 用户看得到那个图标，手指点过去却落在屏幕之外。

### 旧阈值法为什么没救回来

v4.24.0 用一组写死的 dp 阈值决定藏哪几个控件（615 / 557 / 506 / 448）。
那组数字是按**横屏手机**估的，竖屏看横屏视频时对不上 —— 阈值以为放得下，实际差几十 dp。

> 顺带发现旧阈值法本身有两处逻辑倒置：`availDp >= 506` 分支写的是「收下一集」却反而显示，`availDp >= 448` 分支写的是「收画质」却反而显示。整体删除后问题自然消失。

## 三、v4.25.0 的修法

### 3.1 折叠决策从「猜 dp 阈值」改成「量真实宽度」

新增两个类（两版完全一致）：

**`RowFit.java`** —— 纯逻辑折叠算法，不依赖任何 Android API，可在 JVM 直接单测：

```java
public static boolean[] foldMask(int[] widths, int available) {
    boolean[] hide = new boolean[n];
    // 第一遍：宽度 <= 0 的控件「本来就不该显示」，无条件标记隐藏
    int total = 0;
    for (int i = 0; i < n; i++) {
        if (widths[i] <= 0) hide[i] = true;
        else total += widths[i];
    }
    // 第二遍：按优先级（数组顺序）从前往后折叠，直到真的放得下
    for (int i = 0; i < n; i++) {
        if (total <= available) break;
        if (hide[i]) continue;
        total -= widths[i];
        hide[i] = true;
    }
    return hide;
}
```

**`FoldRow.java`** —— 继承 `LinearLayout`，在 `onMeasure` 里按实测宽度折叠：

- 折叠**必须在测量前**决定。`LinearLayout` 是边测边排的：宽度不够时它先把可压缩的文字胶囊挤瘦，挤不下了才把固定宽度的图标推到边界外。等布局完再处理，第一帧就已经错了。
- 宽度**只看业务可见性**，不看当前是否被折叠。否则「折叠 → 宽度记 0 → 算得下 → 放出来 → 反复横跳」。
- 文字宽度**按内容缓存**（控制条时间每秒变一次，不能每次重量）。
- 测量期间抑制 `requestLayout()`，避免多跑一轮布局、控制条闪一下。

### 3.2 固定区永不折叠

```
固定区（永不折叠，223dp）      可折叠区（按优先级依次让位）
┌─────────────────────┐      ① 发弹幕  104dp  ← 最占地方，先让
│ 播放 / 时间 / 弹幕开关 │      ② 下一集  （单 P 视频本来就没有）
│ 更多 / 全屏            │      ③ 画质    83dp
└─────────────────────┘      ④ 倍速    82dp
                             ⑤ 选集    47dp  ← 放最后，优先保住一个
```

- **「更多」「全屏」刻意不注册为可折叠** → 全屏键永远不会跑到屏幕外去。
- 单 P 视频的「下一集」是**业务不可见**（不是折叠），两者分开管，互不干扰。

### 3.3 手机竖屏实际折叠结果

```
固定区 223dp + 可折叠预算 95dp
发弹幕 109 → 折叠
下一集   0 → 折叠（业务不可见）
画质    83 → 折叠
倍速    82 → 折叠
选集    47 → 保留
─────────────────────
最终实占 270dp ≤ 318dp，余量 48dp ✓
```

### 3.4 收起的功能不会丢

「更多」菜单补上了 **发弹幕** 和 **倍速**（原来只有清晰度 / 解码方式 / 缓存 / 复制链接）：

```java
final String[] items = {"清晰度：" + qualityShort(...),
        "解码方式：" + decName(...), "发弹幕", "倍速",
        "缓存到本地", "复制视频链接"};
```

所以窄屏时被收走的按钮，功能一件都不丢。

## 四、玻璃去塑料感：把存在感交给边缘

### 4.1 旧版为什么一眼就是塑料

v4.24.0 的玻璃板叠了**四层白**：

```
乳白雾      0x1E → 0x12
顶部受光    0x26
左上反光    0x1C
磨砂噪点    30 / 22
────────────────────
≈ 40% 的均匀白
```

再加边缘一圈 **0x8E 的均匀纯白描边** —— 均匀、灰白、边界硬、没有任何光学信息。
这就是「磨砂塑料板」的教科书长相。

玻璃片也一样：主体 `0x28 → 0x14` 的乳白雾 + `0x8E → 0x1C` 均匀描边 + `0xC6` 顶棱 → 塑料按钮三特征一个不落。

### 4.2 v4.25.0 的做法

真实玻璃之所以像玻璃，靠的不是 body 有多白，而是**边缘那几道光学**：

| # | 光学 | 作用 | 玻璃板 | 玻璃片 |
|---|---|---|---|---|
| ① | 边缘高光 | 上缘被光打亮，越往下越弱 | `0xC4 → 0x1A` | `0xB4 → 0x1E` |
| ② | 高光热点 | 左上角更亮，避免高光呆板成直线 | `0x78` 径向 | `0x60` 径向 |
| ③ | 接触暗线 | 高光内侧紧挨的细暗线 = 玻璃厚度 | `0x08 → 0x30` 黑 | `0x08 → 0x28` 黑 |
| ④ | 边缘色散 | 左冷右暖的彩色偏移，塑料永远没有 | `0x38A9D8FF → 0x34FFC79A` | `0x30A9D8FF → 0x2CFFC79A` |
| ⑤ | 底缘反光 | 下沿被地面反射托起的一线亮（悬浮感） | `0x55` 水平渐变 | `0x46` 水平渐变 |

身体只留极淡的一层：

```
乳白雾    0x1E → 0x12   →   0x0A → 0x04
顶部受光  0x26          →   0x14
噪点      30 / 22       →   12 / 8
投影      4 层小偏移硬影 →  3 层大范围淡影
```

绘制顺序：**边缘高光 → 高光热点 → 接触暗线 → 边缘色散 → 底缘反光**。

### 4.3 性能

- 着色器按尺寸缓存，尺寸不变不重建（扫光动画每帧重绘也不产生垃圾）；`tint()` 时缓存失效。
- 全场只在控件显示 / 按下 / 扫光时重绘，静止时零开销。
- 无 RenderScript、无 RenderEffect、无额外线程，**API 22 起可用**。
